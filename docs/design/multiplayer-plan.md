# 멀티플레이 기획서 (Issue #367)

> 상태: **초안 v0.1** · 대상 이슈: [stlim0727/flight3d#367 「멀티유저 게임으로 만들자」](https://github.com/stlim0727/flight3d/issues/367)
> 범위: 게임 기능 추가. 같은 공역에서 여러 명이 함께 비행하는 **멀티 시나리오**.
> 이 문서는 무엇을, 왜 만드는지와 규칙을 다룹니다. 구현 세부 사항은 확정되면 `docs/development/`의 개발 문서로 옮깁니다.

---

## 1. 개요

### 1.1 한 줄 요약
**방을 만들면 링크가 생기고, 링크를 연 사람은 모두 같은 하늘에서 함께 비행합니다.** 별도 서버나 설치는 필요 없습니다.

### 1.2 배경
- 지금의 Flight3D는 혼자 하는 게임입니다. 기체 3종, 지형 5곳, 시나리오 7종(활주로, 접근, 순항, 절벽 이륙, 계곡 슬라롬, 한강, 데모)이 모두 1인용입니다.
- 계곡 슬라롬처럼 점수가 있는 미션이 생겼지만 기록 비교는 브라우저 안 로컬 스코어보드(`ValleyScoreboard`)에서만 됩니다.
- 이슈 #367 요구사항:
  1. 방을 만들면 URL이 생기고, 같은 URL로 들어오면 같은 게임에 접속
  2. 오디오(음성) 통신
  3. 활주로가 하나면 기체를 앞뒤로 나란히 줄 세우기
- 이슈 댓글에서 합의된 방향: 정적 웹페이지(GitHub Pages)를 유지하면서 **WebRTC P2P**로 연결합니다. 음성은 미디어 스트림, 게임 데이터는 데이터 채널로 보내고, 방장(호스트)이 방 상태의 권한을 가집니다. 참가 인원은 4~5명이 한계입니다.

### 1.3 목표
| # | 목표 | 측정 방법 |
| --- | --- | --- |
| G1 | 링크 하나로 친구와 바로 같이 난다 | 링크를 연 뒤 다른 참가자 기체가 보이기까지 10초 이내 |
| G2 | 함께 하는 이유가 있다 | 자유 비행 외에 목표가 있는 멀티 시나리오 2종 이상 |
| G3 | 혼자 할 때의 품질을 해치지 않는다 | 1인 플레이 동작, 성능, 테스트 결과가 그대로 유지됨 |
| G4 | 서버 없이 운영한다 | 상시 운영하는 게임 서버 0대(시그널링·TURN은 7장 참고) |

### 1.4 하지 않을 것 (Non-goals, 1차 범위)
- 모르는 사람과 매칭하는 기능, 공개 방 목록
- 공식 랭킹, 치트 방지, 서버 측 채점
- 6명 이상 대규모 세션
- 텍스트 채팅(음성과 프리셋 메시지로 대체)
- 리플레이 공유, 관전 전용 방송

## 2. 타깃과 플레이 상황

| 페르소나 | 상황 | 원하는 것 |
| --- | --- | --- |
| 친구 그룹(2~4명) | 디스코드나 메신저에 링크를 공유 | 설치 없이 바로 같이 날기, 음성으로 떠들기 |
| 교관과 학생 | 한 명이 시범 비행, 한 명은 따라 하기 | 편대 비행, 상대 기체 관전 |
| 경쟁형 유저 | 계곡 슬라롬 기록 경쟁 | 같은 조건에서 동시에 출발해 순위 확인 |
| 모바일 유저 | 폰으로 링크 열기 | 터치 조작으로 참여, 푸시투토크 |

## 3. 핵심 경험 흐름

```
[방장] 로비 → "멀티플레이" → 방 만들기 → 지형·시나리오 선택 → 링크 복사·공유
                                                        │
[참가자] 링크 열기 → 닉네임·기체 선택 → 대기실 입장 ←──────┘
                                    │
                대기실: 참가자 목록 · 준비 상태 · 음성 테스트
                                    │
           방장 "시작" → 카운트다운 → 각자 지정 슬롯에 스폰
                                    │
                 비행(서로의 기체가 보이고 음성 통신)
                                    │
           시나리오 종료 → 합산 결과 화면 → 다시 하기 / 대기실 / 나가기
```

- **코어 루프**: 모이기 → 같은 조건으로 출발 → 함께 비행 또는 경쟁 → 결과 비교 → 다시 하기
- **세션 길이**: 1판 3~10분, 한 방에서 여러 판을 이어서 플레이
- 기존 1인 흐름(로비 → 비행 → 디브리프 → 다시 비행)은 그대로 두고, 멀티는 로비의 새 진입점으로 추가합니다.

## 4. 멀티 시나리오

모든 시나리오는 **같은 지형** 위에서 진행합니다. 지형은 방 단위로 고정하고 방장이 정합니다. 기체는 시나리오가 허용하는 범위에서 각자 고릅니다.

### 4.1 시나리오 목록과 우선순위

| ID | 이름 | 핵심 재미 | 지형 | 기체 | 인원 | 우선순위 |
| --- | --- | --- | --- | --- | --- | --- |
| `mp-free` | 공역 공유 자유 비행 | 같이 날고 구경하기 | 전체 | 자유 | 2~4 | **P0** (MVP) |
| `mp-lineup` | 순차 이륙 (활주로 줄서기) | 이슈 요구사항 3, 질서 있게 출발 | coastal, incheon, neon | 자유 | 2~4 | **P0** (MVP) |
| `mp-formation` | 편대 비행 | 리더를 따라 정해진 위치 유지 | coastal, incheon, hangang | 같은 기종 권장 | 2~4 | P1 |
| `mp-slalom-race` | 계곡 슬라롬 레이스 | 같은 코스 동시 출발, 순위 | lukla | F16 | 2~4 | P1 |
| `mp-pattern` | 트래픽 패턴 순차 착륙 | 간격 유지하며 차례로 착륙 | coastal, incheon | 자유 | 2~4 | P2 |

### 4.2 `mp-free` 공역 공유 자유 비행
- **목표**: 정해진 목표 없음. 서로의 기체를 보며 자유롭게 비행합니다.
- **시작**: 방장이 고른 1인용 시나리오(활주로, 접근, 순항)의 스폰 지점을 슬롯별로 나눠 배치합니다(4.3, 4.7 참고).
- **기체 간 충돌**: 기본값 **OFF**(고스트). 방 옵션으로 ON을 허용합니다.
- **종료**: 각자 자유롭게 종료하고 개인 디브리프로 넘어갑니다. 방에는 남습니다.
- **추락 시**: 개인 리셋 후 같은 방에 다시 스폰합니다. 다른 참가자에게는 영향이 없습니다.

### 4.3 `mp-lineup` 순차 이륙 (이슈 요구사항 3)
- **배치**: 활주로 시단부터 슬롯 1, 2, 3, 4 순서로 **활주로 중심선 위에 앞뒤로** 세웁니다.
  - 기본 간격은 기체 길이와 후류를 고려해 정합니다. 예) B738 60m, C172·F16 30m. 기종이 섞이면 앞 슬롯 기체를 기준으로 합니다.
  - 활주로 길이에서 필요한 이륙 거리를 뺀 범위 안에 모든 슬롯이 들어가야 합니다(Coastal 3,200m 기준 4대 여유). 들어가지 않으면 남는 슬롯을 유도로 대기 지점에 배치합니다.
  - Lukla(527m 경사 활주로)에는 이 시나리오를 제공하지 않습니다.
- **진행**: 슬롯 1부터 차례로 **이륙 허가**를 받습니다. 기존 출발 ATC·무전(`departureAtc.js`, `departureRadio.js`)을 재사용하고, 호출부호는 참가자 닉네임으로 대신합니다.
  - 다음 허가 조건: 앞 기체가 이륙하고 일정 거리(예: 활주로 끝 통과)를 지나거나, 일정 시간(예: 45초)이 지난 경우
  - 허가 전에 출발하면 **조기 출발** 페널티를 줍니다(점수 감점, 실격 아님).
- **평가**: 정시 이륙(허가 후 반응 시간), 활주로 중심선 유지, 이륙 후 지정 고도와 방위 도달
- **종료**: 마지막 기체가 지정 고도에 도달하면 합산 결과를 보여주고, 이어서 `mp-free`로 계속 비행할지 선택합니다.

### 4.4 `mp-formation` 편대 비행
- **역할**: 리더 1명(방장이 지정, 기본값은 방장), 나머지는 윙맨. 윙맨마다 지정 위치(좌우 후방 오프셋)를 줍니다.
- **진행**: 리더는 자유롭게 비행하고, 윙맨은 지정 위치를 유지합니다. 시간 제한은 3~5분입니다.
- **평가**: 지정 위치 대비 거리 오차의 시간 평균, 위치 유지 시간 비율. 리더는 급기동이 적을수록 보너스를 받습니다(부드러운 리드).
- **화면**: 윙맨 HUD에 지정 위치 마커와 거리·고도차를 표시합니다.
- **충돌**: 편대는 거리가 가까우므로 기본값 ON. 충돌하면 해당 두 기체 모두 추락 처리합니다.

### 4.5 `mp-slalom-race` 계곡 슬라롬 레이스
- 기존 F16 Lukla 계곡 슬라롬(`SlalomMission`, `valleyCourse`)의 코스, 판정, 점수 규칙을 **그대로** 씁니다.
- 방장이 코스 시드와 환경 프로필을 정하면 모든 참가자가 **같은 조건(comparisonKey)**으로 동시에 출발합니다.
- 기체 간 충돌은 OFF(고스트). 레이스의 공정성이 위치 동기화 지연에 흔들리지 않게 하려는 것입니다.
- **결과**: 각자 자기 클라이언트에서 판정한 결과를 방장이 모아 순위표를 만듭니다. 비공식 순위이므로 치트 방지는 하지 않습니다.
- 사람과 AI 파일럿이 섞인 레이스는 P2에서 검토합니다.

### 4.6 `mp-pattern` 트래픽 패턴 순차 착륙 (P2)
- 공중의 지정 진입점에서 차례로 시작해 장주를 돌고 착륙합니다. 평가 항목은 앞 기체와의 간격, 접지 품질(기존 디브리프 지표), 복행 여부입니다.

### 4.7 공통 규칙
| 항목 | 규칙 |
| --- | --- |
| 지형 | 방 단위 고정, 방장이 선택. 변경하면 모두 다시 스폰 |
| 기체 | 시나리오가 허용하는 기종 안에서 각자 선택 |
| 바람·날씨·시간대 | 방장 설정을 모든 참가자에게 동일하게 적용(시드 공유) |
| 일시정지 | 멀티에서는 내 화면만 메뉴로 넘어가고 내 기체는 계속 비행. 경쟁 시나리오 중에는 메뉴를 열면 기권 확인 |
| 중도 참가 | `mp-free`는 즉시 참가. 진행 중인 경쟁 시나리오에는 관전자로 들어오고 다음 판부터 참가 |
| 연결 끊김 | 15초 안에 재접속하면 같은 슬롯으로 복귀. 넘으면 퇴장 처리하고 기체는 화면에서 사라짐 |

## 5. 시스템 설계 (기획 관점)

### 5.1 방과 URL
- 방을 만들면 `?room=<방ID>` 형식의 링크가 생깁니다. 방 ID는 사람이 읽기 쉬운 6~8자 무작위 문자열(예: `K7QM2X`)입니다.
- 링크에는 방 ID만 담습니다. 지형, 시나리오 등의 설정은 접속 뒤 방장에게서 받습니다. 기존 URL 파라미터처럼 **URL로 코드를 실행하거나 임의 값을 주입하지 않습니다.**
- 방장이 나가면 남은 참가자 중 가장 먼저 들어온 사람이 방장을 넘겨받습니다(호스트 마이그레이션, P1). MVP에서는 방이 종료됩니다.
- 공유 수단: 링크 복사 버튼, Web Share API(모바일), QR 코드(P1)

### 5.2 권한 모델 (누가 무엇을 결정하나)
| 대상 | 결정 주체 | 이유 |
| --- | --- | --- |
| 내 기체의 물리(위치, 자세, 손상) | **각자 자기 클라이언트** | 기존 120Hz 물리를 그대로 쓰고 조작 지연을 없애기 위해 |
| 지형·추락(지형, 건물, 착륙 손상) | 각자 자기 클라이언트 | 기존 충돌 판정을 재사용 |
| 방 상태(참가자, 슬롯, 시나리오 단계, 카운트다운, 이륙 허가) | **방장** | 순서와 진행이 하나로 일치해야 함 |
| 기체 간 충돌 판정 | 방장 | 두 클라이언트의 판정이 엇갈리는 것을 막기 위해. 결과는 양쪽에 통보 |
| 시나리오 점수 | 각자 계산 → 방장이 집계 | 기존 미션 판정 코드를 재사용, 비공식 순위 |

- 다른 참가자의 기체는 **보여주기용**입니다. 내 기체의 물리에 힘을 주지 않습니다(충돌이 ON일 때의 충돌 이벤트만 예외).
- 방장 클라이언트도 일반 참가자와 똑같이 비행합니다. 별도 서버 역할은 없습니다.

### 5.3 동기화 (요구 수준)
- **전송 정보**: 위치, 자세, 속도, 조종면, 기어, 플랩, 조명, 스로틀(엔진음), 추락 여부. 1인당 약 100바이트입니다.
- **전송 주기**: 15Hz 기본, 거리가 멀면 5Hz로 낮춥니다.
- **표시**: 수신한 상태를 약 100~150ms 버퍼로 보간합니다. 패킷이 끊기면 짧은 시간만 외삽하고, 0.5초가 넘으면 마지막 위치에 고정한 뒤 "연결 불안정" 표시를 띄웁니다.
- **목표 품질**: 보간된 상대 기체의 위치 오차가 일반 비행에서 기체 길이 이하일 것(4명, 일반 가정 네트워크 기준)
- **시간 기준**: 카운트다운과 레이스 시작은 방장 시계 기준이고, 접속 시 시계 오프셋을 측정해 보정합니다.

### 5.4 음성 통신 (이슈 요구사항 2)
- 기본값은 **푸시투토크(PTT)**입니다. 데스크톱은 키 하나(예: `V`, 기존 키 배치와 겹치지 않는 키로 확정), 모바일은 화면의 PTT 버튼을 씁니다.
- 옵션: 항상 켜기(음성 감지), 참가자별 음소거와 볼륨 조절
- 마이크 권한은 대기실에서 요청하고, 거부해도 듣기만으로 참여할 수 있습니다.
- 무전 느낌을 내는 필터(밴드패스, 잡음)는 P1 옵션으로 둡니다.
- 말하는 사람은 명단과 기체 이름표에 표시합니다.
- 음성 없이 쓰는 **프리셋 메시지**: "이륙합니다", "따라오세요", "복행" 등(P1)

### 5.5 호출부호와 표시
- 닉네임 최대 12자. 정하지 않으면 `기종-번호`(예: `C172-2`)로 자동 지정합니다.
- 다른 기체 위에 이름표, 거리, 고도를 표시하고 거리에 따라 크기를 줄입니다. 설정에서 끌 수 있습니다.
- 미니 명단: 참가자, 기종, 상태(비행 중, 추락, 관전), 음성 아이콘

### 5.6 관전
- 추락했거나 관전 중인 사람은 다른 참가자의 기체를 골라 외부 시점으로 따라갈 수 있습니다(기존 외부 카메라를 재사용).

## 7. 기술 조건과 제약

| 항목 | 내용 |
| --- | --- |
| 배포 | 지금처럼 정적 사이트(GitHub Pages, HTTPS)를 유지합니다. HTTPS는 마이크 권한 요건도 충족합니다 |
| 연결 | WebRTC 메시(최대 4명 권장, 5명 상한). 데이터 채널(게임 상태)과 미디어 스트림(음성) |
| 시그널링 | 처음 연결할 때만 필요합니다. 후보: PeerJS 공개 서버(빠른 시작) 또는 직접 운영하는 소형 시그널링. **결정 필요(10장)** |
| NAT 통과 | STUN만으로는 일부 네트워크(회사, 학교, 일부 이동통신망)에서 연결에 실패합니다. TURN 릴레이 사용 여부 **결정 필요** |
| 성능 | 상대 기체 3대를 추가로 그려도 모바일 기준 프레임 저하가 작아야 합니다. 원거리 기체는 저해상도 모델 또는 단순 모델로 표시 |
| 대역폭 | 상태 데이터는 1인당 수 KB/s 이하. 음성은 1인당 약 30~50kbps × (인원 − 1) |
| 기존 코드 영향 | 물리 엔진(`PhysicsIntegrator`), 시나리오 레지스트리(`scenarioRegistry.js`), 스폰(`PresetSpawner`), 미션(`src/arena/`)은 재사용하고, 멀티 계층은 이것들을 감싸는 형태로 추가합니다. 1인 플레이 코드 경로는 바꾸지 않습니다 |
| 개인정보 | P2P 특성상 참가자끼리 IP가 노출될 수 있습니다. 참가 화면에서 고지합니다. 닉네임과 음성은 저장하지 않습니다 |

## 9. 검증과 수용 기준

### 9.1 수용 기준 (M1)
- [ ] 방을 만들면 링크가 생기고, 다른 브라우저에서 그 링크를 열면 같은 대기실에 들어간다
- [ ] 방장이 시작하면 모든 참가자가 같은 지형, 같은 바람 조건으로 지정 슬롯에 스폰된다
- [ ] `mp-lineup`에서 기체가 활주로 중심선 위에 앞뒤로 겹치지 않게 배치되고, 차례대로 이륙 허가를 받는다
- [ ] 상대 기체의 위치, 자세, 기어, 조명이 보이고 15Hz 수신 기준으로 끊김 없이 보간된다
- [ ] PTT를 누르는 동안에만 내 음성이 전달되고, 말하는 사람이 표시된다
- [ ] 한 명이 추락하거나 나가도 다른 참가자의 비행은 계속된다
- [ ] `?room=` 없이 접속하면 1인 플레이가 이전과 똑같이 동작한다(기존 테스트 전부 통과)
- [ ] 데스크톱(Chrome)과 모바일(Android Chrome, iOS Safari) 조합에서 연결된다

### 9.2 테스트 방법
- **로직 테스트(Node)**: 슬롯 배치 계산, 이륙 허가 순서, 방 상태 전이, 보간과 외삽, 점수 집계
- **브라우저 시나리오**: 같은 머신에서 브라우저 컨텍스트 2개 이상으로 접속 흐름 자동 검증(하드웨어 GPU 정책은 `docs/development/browser-gpu.md`를 따름)
- **실사용 플레이테스트**: 서로 다른 네트워크(가정 Wi-Fi와 이동통신망)에서 4명 세션 3회 이상
- **수집 지표(세션 내 표시)**: 연결 성공률, 평균 지연(RTT), 재접속 횟수, 판당 완주율

## 부록 A. 용어
- **방장(호스트)**: 방을 만든 참가자. 방 상태 권한을 가짐

- **시그널링**: WebRTC 연결을 맺으려고 처음에 접속 정보를 교환하는 과정
